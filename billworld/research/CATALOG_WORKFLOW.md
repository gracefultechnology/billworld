# Recovering a DNS failure burst

The main frontend supervisor stops with `dns_failure_burst` (exit 3) when a batch has at least ten direct DNS failures, at least 80% of its requests fail that way, and those failures span at least three hosts. This is a diagnostic stop, not proof that the domains are permanently unavailable. It bounds damage from a resolver outage without automatically retrying an unlimited queue. Attempt evidence stays intact.

After confirming that the collector is stopped and affected hosts resolve again, use `python3 -m billworld.research_frontend_recovery --since <UTC-timestamp> --until <UTC-timestamp> --limit 1000 --output <new-receipt.json>`. The time window is inclusive at the start and exclusive at the end. Each call requeues at most 10,000 existing `gaierror` failures, retains the old evidence in `dns_requeues` in the same database transaction, and leaves the attempt history unchanged. Repeated bounded calls advance past already pending entries. Successful captures, HTTP errors, malformed URLs and failures outside the window are excluded. The command shares the main supervisor lock; it makes no network requests. Run a small controlled retry first, then resume the ordinary public-GET collector with its disk reserve. Legacy direct batch commands must not run concurrently.

The October 5 investigation and recovery are recorded in `frontend-dns-recovery-validation.json`. Requeued work is pending evidence collection, not recovered source coverage.

HTTP transport now percent-encodes spaces and Unicode in source paths/queries and applies IDNA to hostnames while retaining the original requested URL and recording any changed transport URL. Existing percent escapes and query separators remain intact. Redirects use the same encoding and public-address checks. This repairs valid references such as SharePoint `Style Library` paths without guessing a replacement route or changing catalog URL identities. Control characters and credential-bearing URLs remain rejected.
